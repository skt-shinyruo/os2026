# crepl Lab 实现思路

这份说明是给初学者看的。目标不是一下子把所有细节都讲成系统编程教材，而是先帮你建立一个正确的整体图景：

- 这个 lab 到底要做什么
- 为什么要这样做
- 程序运行时内部发生了什么
- 你可以按什么顺序把它写出来

---

## 1. 这个 lab 本质上是在做什么？

一句话：

**做一个“会调用 gcc 的 C 语言计算器”。**

用户每输入一行代码，你的程序就要判断：

- 这是一条函数定义？
- 还是一个表达式？

然后把它变成可以被 `gcc` 编译的代码，编译成共享库，再动态加载回来执行。

所以它不是传统意义上的“解释器”。

它更像这样：

```text
读入一行字符串
    ↓
生成临时代码
    ↓
调用 gcc 编译
    ↓
把编译结果加载到当前进程
    ↓
执行并得到结果
```

---

## 2. 为什么不能直接执行表达式字符串？

很多初学者会下意识地想：

> 用户输入 `1 + 2 * 3`，我能不能直接“算”出来？

对于 Python、JavaScript 这类语言，可能有 `eval()` 一类机制。  
但 C 语言本身没有“把一段字符串当作代码直接执行”的标准能力。

所以这题的核心技巧就是：

**不要直接执行字符串，而是把字符串写成 C 代码文件，再交给 gcc 编译。**

---

## 3. 题目里有哪两种输入？

题目只要求你处理两种输入：

### 3.1 函数定义

例如：

```c
int add(int a, int b) { return a + b; }
```

如果一行以 `int` 开头，就把它当成函数定义。

你需要做的是：

1. 把它写进临时 `.c` 文件
2. 用 `gcc` 编译成 `.so`
3. 用 `dlopen()` 加载
4. 以后允许其他函数或表达式调用它

### 3.2 表达式

例如：

```c
add(3, 4) * 10
```

如果一行不是以 `int` 开头，就把它当成表达式。

你需要做的是：

1. 把表达式包进一个 wrapper function
2. 编译成 `.so`
3. 加载
4. 找到这个 wrapper
5. 调用它，得到返回值

---

## 4. 为什么表达式要包一层 wrapper？

因为像下面这样：

```c
1 + 2 * 3
```

它不是完整的 C 程序，也不是函数定义，`gcc` 不能直接编译它。

所以要把它变成这样：

```c
int __expr_wrapper_1() {
    return 1 + 2 * 3;
}
```

这样它就变成了一个正常的函数，可以被编译、加载、调用。

这就是题目说的 **wrapper function**。

---

## 5. 程序内部是怎么一步一步运行的？

假设用户运行你的 `crepl` 后，依次输入：

```c
int add(int a, int b) { return a + b; }
add(3, 4) * 10
```

### 5.1 第一行：函数定义

程序看到：

```c
int add(int a, int b) { return a + b; }
```

因为它以 `int` 开头，所以判断为函数定义。

接下来内部流程大概是：

1. 生成一个临时源文件，比如 `/tmp/crepl_1.c`
2. 把函数定义写进去
3. 调用 gcc 编译成 `/tmp/crepl_1.so`
4. 用 `dlopen("/tmp/crepl_1.so", RTLD_NOW | RTLD_GLOBAL)` 加载
5. 把函数名 `add` 记录下来
6. 输出 `OK.`

### 5.2 第二行：表达式

程序看到：

```c
add(3, 4) * 10
```

因为它不是以 `int` 开头，所以判断为表达式。

接下来内部流程大概是：

1. 生成另一个临时源文件 `/tmp/crepl_2.c`
2. 因为表达式里用到了 `add`，所以先写函数声明
3. 再生成 wrapper function
4. 调用 gcc 编译成 `/tmp/crepl_2.so`
5. `dlopen()` 加载
6. `dlsym()` 找到 wrapper 的地址
7. 调用 wrapper，返回值是 `70`
8. 打印 `= 70`

这个临时文件的内容可能像这样：

```c
int add(int, int);

int __expr_wrapper_2() {
    return add(3, 4) * 10;
}
```

## 6. 为什么还要写函数声明？

这是很多人第一次读题时最容易忽略的地方。

假设你之前定义过：

```c
int add(int a, int b) { return a + b; }
```

后面又输入：

```c
add(3, 4) * 10
```

当 gcc 编译 wrapper 的时候，它必须先知道 `add` 是个函数。  
否则编译器可能会报错。

所以你需要维护一个“之前定义过哪些函数”的列表。  
每次生成新的 `.c` 文件时，先把这些声明写进去，比如：

```c
int add(int, int);
int fib(int);
int gcd(int, int);
```

然后再写当前这次要编译的内容。

---

## 7. 为什么要用 `.so` 和 `dlopen()`？

因为题目要求的是：

- 函数被加载到 **当前进程**
- 之后输入的表达式和函数可以继续调用前面定义过的函数

如果你编译成普通可执行文件再运行，那就是开了一个新进程。  
新进程退出之后，代码不会留在当前 `crepl` 进程里。

而共享库 `.so` 可以通过：

- `dlopen()` 加载
- `dlsym()` 找函数地址

这样代码就进入了当前进程的地址空间。

这正是这个实验要你练习的东西。

---

## 8. 为什么题目不让用 `system()`？

因为老师想让你练习真正的进程控制和系统调用。

错误做法：

```c
system("gcc ...");
```

题目明确禁止。

你应该这样做：

1. `fork()`
2. 子进程里 `execlp("gcc", ...)`
3. 父进程里 `waitpid()`
4. 判断 gcc 是否成功退出

也就是说，这题不只是让你“会写字符串拼命令”，而是让你真正碰一遍：

- 创建进程
- 替换程序映像
- 等待子进程结束

## 9. 这个 lab 最容易理解的实现拆分

结合 `crepl.c` 这个骨架，最容易上手的拆法是下面这样。

### 9.1 `main()`

作用：

**不断从标准输入读一行，然后分流给不同函数处理。**

伪代码：

```c
while (fgets(line, sizeof(line), stdin)) {
    去掉末尾换行;
    跳过空行;

    if (这一行以 int 开头) {
        compile_and_load_function(line);
    } else {
        evaluate_expression(line, &result);
    }
}
```

### 9.2 `compile_and_load_function(const char *function_def)`

作用：

**把函数定义编译成共享库并加载。**

它内部主要做这些事：

1. 从函数定义里提取函数名
2. 生成临时 `.c` 文件和 `.so` 文件路径
3. 把之前定义过的函数声明写进 `.c`
4. 再把当前函数定义写进去
5. `fork + exec gcc` 编译
6. 如果编译成功，用 `dlopen()` 加载
7. 成功后把函数名记录到全局列表

### 9.3 `evaluate_expression(const char *expression, int *result)`

作用：

**把表达式包成 wrapper function，编译并执行。**

它内部主要做这些事：

1. 生成一个唯一的 wrapper 名字，比如 `__expr_wrapper_7`
2. 生成临时 `.c` 和 `.so`
3. 先写之前定义过的函数声明
4. 写：

```c
int __expr_wrapper_7() {
    return 表达式;
}
```

5. 调 gcc 编译
6. `dlopen()` 加载
7. `dlsym()` 找到 `__expr_wrapper_7`
8. 调这个函数
9. 把返回值写入 `*result`

### 9.4 辅助函数

建议再拆几个小函数，让代码更清楚：

- `trim_newline()`
- `is_function_definition()`
- `extract_function_name()`
- `write_known_function_decls()`
- `compile_shared_object()`

## 10. 你需要维护哪些全局状态？

通常有这几类就够了。

### 10.1 已定义函数名列表

例如：

```c
char *defined_functions[100];
int defined_count;
```

用途：

- 以后生成新源码时，写入这些函数声明

### 10.2 唯一编号

例如：

```c
int next_id = 0;
```

用途：

- 给临时文件起不同名字
- 给 wrapper function 起不同名字

比如：

- `/tmp/crepl_1.c`
- `/tmp/crepl_1.so`
- `__expr_wrapper_1`

这样就不会重名。

### 10.3 已加载共享库句柄（可选）

例如：

```c
void *handles[100];
int handle_count;
```

这不是绝对必须，但有时你可能想保留句柄。

实际上这个 lab 里，即使你不主动 `dlclose()`，让它们一直留到程序结束也没问题。

## 11. 为什么 `RTLD_GLOBAL` 很重要？

加载共享库时，你大概率会写：

```c
dlopen(path, RTLD_NOW | RTLD_GLOBAL);
```

这里的 `RTLD_GLOBAL` 很重要。

原因是：

- 你先加载了 `add`
- 后面又加载了一个表达式 wrapper
- wrapper 里面调用了 `add`

如果前面加载的符号没有放到“全局可见”范围里，后面新加载的 `.so` 可能找不到它。

所以：

- `RTLD_NOW`：立即解析符号
- `RTLD_GLOBAL`：让之后加载的库也能看到这些符号

## 12. 错误处理需要做到什么程度？

题目并没有要求你做一个工业级 REPL。

你只要做到：

- 编译失败时返回 `false`
- `dlopen()` 失败时返回 `false`
- `dlsym()` 失败时返回 `false`
- 程序不要 crash

也就是说，**允许报错，不允许崩溃**。

例如这些情况都可能失败：

- 用户输错了函数语法
- 表达式不合法
- 调用了不存在的函数
- gcc 编译失败
- 动态加载失败

你都可以打印一条简单错误信息，然后继续读下一行。

## 13. 作为初学者，建议你按什么顺序实现？

不要一上来就把所有功能一起写。  
最稳的顺序是：

### 第一步：先实现“表达式求值”

先只处理最简单的表达式，比如：

```c
42
21 + 21
```

这一阶段你甚至不用支持“调用之前定义的函数”。

只要能做到：

- 生成 wrapper
- 编译成 `.so`
- `dlopen + dlsym`
- 调用后拿到结果

你就已经完成了这个 lab 最关键的一半。

### 第二步：实现“函数定义加载”

让下面这种输入能成功：

```c
int test() { return 42; }
```

也就是：

- 编译函数定义
- 加载成功
- 记录函数名

### 第三步：让表达式能调用之前定义的函数

例如：

```c
int test() { return 42; }
test() + 1
```

这一阶段你要补的是：

- 写入旧函数声明
- 使用 `RTLD_GLOBAL`

### 第四步：补错误处理

确保这些情况不会让程序崩：

- 非法语法
- 未定义函数
- gcc 编译失败
- `dlopen` 失败

对于最小可过版本，很多东西不用一开始就做复杂。

比如：

- 不需要做完整的 C 语法解析

- 不需要支持标准库函数

你只要满足题目最小要求就行：

- 识别 `int` 开头的是函数定义
- 其他一律按表达式处理
- 编译
- 加载
- 执行

## 15. 初学者最容易卡住的几个问题

### 15.1 “表达式怎么执行？”

不是直接执行字符串。

而是先生成：

```c
int __expr_wrapper_x() {
    return 你的表达式;
}
```

然后编译、加载、调用这个函数。

### 15.2 “前面定义的函数为什么后面还能调用？”

因为：

1. 你把那个函数编译成了 `.so`
2. 用 `dlopen(..., RTLD_GLOBAL)` 加载进当前进程
3. 后面生成新代码时，又补上了它的函数声明

所以后面的代码可以继续引用它。

### 15.3 “为什么一定要记录函数名？”

因为以后再生成新的源码时，你要先写声明。

如果你不知道之前有哪些函数，就没法写：

```c
int add(int, int);
int fib(int);
```

### 15.4 “要不要自己解析参数类型和参数名？”

对于这个 lab，题目已经说得比较宽松。  
你可以只支持 `int`，而且测试不会故意为难你。

如果你暂时不想完整解析参数列表，可以先走“宽松可用”的方案，后面再逐步完善。

## 17. 对照代码骨架时应该重点看什么？

在 `crepl/crepl.c` 里，最重要的三个部分是：

- `main()`
- `compile_and_load_function()`
- `evaluate_expression()`

你写代码时，建议一直问自己：

1. 这一行输入现在是函数还是表达式？
2. 我要生成什么临时代码？
3. gcc 编译成功了吗？
4. 共享库加载成功了吗？
5. 如果是表达式，wrapper 调用成功了吗？

这个 lab 的难点不是算法，而是：

- 理解动态编译
- 理解动态加载
- 理解进程与共享库之间的关系

---

## 18. 一句话总结

这题不是让你“写一个真正的 C 解释器”。

这题是在让你：

**把用户输入的单行 C 代码，临时拼成源文件，用 gcc 编译成共享库，再动态加载执行。**

如果你能把这句话彻底理解，整个 lab 的方向就不会错。
