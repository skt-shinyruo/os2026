# M5 Lab 初学者解读

## 这题本质在做什么

这不是一道“写个 `malloc` 就行”的题，而是在让你做一个“操作系统风格的、支持并发的内存分配器”。

你实际要补的是 `mymalloc.c` 里的：

- `mymalloc(size_t size)`
- `myfree(void *ptr)`

接口定义在 `mymalloc.h`，底层会给你：

- `vmalloc(void *addr, size_t length)`
- `vmfree(void *addr, size_t length)`

可以把它理解成两层：

1. `vmalloc/vmfree` 负责拿大块、页对齐的内存。
2. 你的 `mymalloc/myfree` 负责把这些大块管理成很多小块，正确地分配和回收。

## 你最终要做到什么

按 `M5.md` 的要求，这个 lab 主要考 4 件事：

- 正确性：每次 `mymalloc(size)` 返回一段可用内存，不能和已经分配过的区间重叠。
- 可回收性：`myfree(ptr)` 要能准确释放之前分配的那一块。
- 并发安全：多个处理器或线程同时分配和释放时，内部状态不能乱。
- 可扩展性：不能只是“加一把大锁凑合能跑”；Online Judge 会测多处理器性能，锁竞争太严重会失败。

## 这题为什么不只是“实现功能”

这题最容易误判的地方，是你以为“能过几个简单测试就差不多了”，但题目真正卡的是这些隐藏要求：

- 不能只在单线程下正确。
- 不能只在常见情况正确，边角并发 bug 也可能被测出来。
- 不能浪费太多内存。题目要求实际使用内存不能超过申请内存的 4 倍太多。
- 不能大量依赖静态区。代码、数据、bss 总共不能超过 1 MiB。
- 最终环境是 freestanding，不是普通用户态程序。你本地可以方便测试，但提交代码不能依赖普通 libc 环境才能工作。

## 你现在最该怎么理解这题

对初学者来说，先不要把它看成“高级优化题”，先把任务边界想清楚：

- 这题不是让你设计一个炫的数据结构竞赛题。
- 这题是在实现一个“内存分配服务”。
- 这个服务要同时满足：分得对、收得回、多人同时用不出错、性能别太差。
- 题目还明确说了：不要用区间树，重点是系统设计，不是花哨结构。

## 仓库里哪些文件最值得先看

- `M5.md`：题目要求本身。
- `mymalloc/mymalloc.h`：你要实现的接口。
- `mymalloc/start.c`：freestanding 和本地测试环境的区别。
- `mymalloc/tests/tests-trivial.c`：只是演示测试，不代表真正难度。

## 开始写代码前，必须先想清楚的 8 个问题

### 1. `mymalloc(size)` 成功时到底承诺了什么？

你要从题目里读出“成功分配”的精确定义：返回的是哪一类地址、这段区间和已有区间必须满足什么关系、调用后整体状态发生了什么变化。

如果这个接口契约没有先想清楚，后面实现很容易变成“碰巧能跑”。

### 2. `myfree(ptr)` 为什么比表面上更难？

从接口看它只收一个指针，但题目要求释放的是“之前某次分配出的完整区间”。

这意味着你必须先想清楚：仅凭 `ptr`，系统内部需要知道哪些信息，才能把对应块正确删掉。

### 3. 这题管理的到底是“已分配块”还是“空闲块”？

题目形式化描述的是“已分配区间集合”。

但真实实现时，你又会自然想到“剩余空闲空间”。初学者很容易在这两个视角之间来回切换，结果把状态维护写乱。你需要先统一自己的抽象对象。

### 4. `vmalloc/vmfree` 和 `mymalloc/myfree` 的分工是什么？

`vmalloc/vmfree` 不是最终答案，它只是更底层的大块内存来源。

你要先分清：哪些责任属于“向系统拿大块”，哪些责任属于“在大块里切小块并复用”。这题核心其实在第二层。

### 5. 为什么“单线程能跑”远远不够？

题目从一开始就在强调多处理器并行申请内存和 scalability。

所以你不能只问“逻辑对不对”，还要问“多个线程同时改内部状态时会不会互相踩坏”。这决定了你必须先列出系统中有哪些共享状态。

### 6. 为什么一把大锁不是终点？

框架已经给了自旋锁，而且模板里甚至放了一个 `big_lock`。

这明显是在提醒你：最直接的同步方式很容易想到，但题目后面又要求并发性能。所以你需要先分辨“能保证正确”和“能通过性能测试”是两层要求。

### 7. 为什么题目特别强调“不要浪费内存”和“不要用太多静态内存”？

题目给了两个硬约束：

- 静态区总量不能太大。
- 总体内存使用不能膨胀到申请量的 4 倍以上。

这说明你不只是要“能分配”，还要控制元数据开销和碎片。

初学者常犯的错是：为了简单，顺手开一堆固定大数组，或者回收后根本不能有效复用。

### 8. 这题真正难点为什么在“测试”而不是“写代码”？

题目已经明说，能过冒烟测试不代表正确。

真正麻烦的是那些低概率并发错误，它们通常只在压力下出现，而且日志还可能改变行为。也就是说，这题不是“写完就结束”，而是“你能不能构造出足够狠的测试去证明自己没骗自己”。

## 这 8 个问题该怎么用


先别急着写实现，先试着把每个问题用自己的话回答成 2 到 4 句话。

只要其中有 2 到 3 个问题答不顺，说明你还不该开写。


  - 用“块头 + 空闲链表”的思路管理小块，不要用区间树。
  - 每个通过 vmalloc 拿到的大块区域，内部切成很多 block；每个 block 至少要记录：
      - 大小
      - 是否空闲
      - 前后相邻 block 的信息，或能支持合并的信息
      - 空闲链表指针

  - mymalloc(size) 的核心流程：
      - 把 size 向上对齐
      - 在某个空闲链表/空闲块集合里找足够大的块
      - 找到后必要时切分
      - 标记为已分配
      - 返回用户区地址，不是头部地址
      - 如果找不到，再调用 vmalloc 扩容一个新的大区域

  - myfree(ptr) 的核心流程：
      - 从用户指针退回到块头
      - 标记为空闲
      - 尝试和左右相邻空闲块合并
      - 把合并后的块重新挂回空闲结构

  - 并发上至少要先做到：
      - 所有共享元数据修改都在锁保护下
      - 不要让 myfree 和 mymalloc 同时把同一块状态改乱

  - 性能上别停在“一把全局大锁 + 单个全局空闲链表”：
      - 最朴素版本能帮助你先跑通
      - 但 OJ 可能会卡扩展性，所以后面通常要按 size class 或按线程/arena 分流，减
        少锁竞争

  - 元数据不要靠大静态数组存：
      - 题目要求静态区很小
      - 元数据最好跟着堆块一起放在动态申请的大区域里

你可以先自己写第一个可运行版本，只追求这三件事：

  - 单线程下 malloc/free 正确
  - free 后能复用
  - 相邻空闲块能合并

## 本地怎么跑测试

直接在仓库根目录运行：

```bash
make test
```

说明：

- `make test` 会转到 `mymalloc/` 目录，编译本地测试二进制到 `/tmp/mymalloc-tests`。
- 运行时会自动启用 `TK_VERBOSE=1`，所以失败时会打印 TestKit 的详细输出。
- 当前 `tests/tests-trivial.c` 里已经放了多组 `SystemTest`，直接跑 `make test` 即可。
